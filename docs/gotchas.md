# 踩过的坑

**这份文档的目的是阻止「后来的人把必要的复杂度简化掉」。**

代码里某些地方看起来绕，几乎每处都有原因，而且原因通常不在代码里。
想简化之前先在这里找一找。

每条格式：**现象 → 根因 → 修法 → 可推广的教训**。

---

## 1. `pmset -g` 的分隔符是混用的（TAB 和空格）

**现象**
日志持续输出「检测到 `disablesleep` 被外部改回，立即恢复」，约每 3 秒一条。
但系统里的值**一直是 1，没有任何程序在跟 Deep Sleep 抢控制权**。

**根因**
`pmset -g` 的输出分隔符不统一：

```
System-wide power settings:
 SleepDisabled		1        ← TAB
Currently in use:
 standby              0        ← 空格对齐
```

解析按空格切分，`SleepDisabled` 那行切不出两段，被 `guard parts.count == 2`
整行跳过 → 每轮对账都判定「值不是 1」→ 无条件重写一遍 → 下一轮重复。

写入本身是成功的，所以系统状态一直正确，**只有日志在空转**。

**更糟的一点**：这段解析在 app 与助手**各有一份**，同一个 bug 存在两处。

**修法**
- 提取到 `Shared/PMSetOutput.swift`，两边共用一份
- 加回归测试 `scripts/test-pmset-parse.swift`（直接编译真实源码、喂真实输出）
- 补一道防御：助手读数里缺少 `SleepDisabled` 键时**不当作「值为 0」**，
  而是回退到本地读取

**教训**
- 「日志说有问题」和「真的有问题」是两件事。日志本身也是代码，也会错。
- 判断「是不是自己改的」要用**自己代码里有没有这条路径** + **历史计数**来证明，
  不能靠感觉。当时用「助手日志里 `enabled: 0` 出现 0 次」直接排除了自身嫌疑。
- 同一逻辑不要存两份副本。这个项目的另一条对应约定是：
  测试**编译真实源码**，而不是复制一份逻辑来测。

## 2. 助手日志里每行出现两次

**现象**
助手日志里每条记录都出现两遍，看起来像「每个命令都被执行了两次」。

排查一度沿着「是不是代码里调用了两次」去找，白花了不少时间。

**根因**
LaunchDaemon 的 `StandardOutPath` 与 `StandardErrorPath`
**都指向同一个日志文件**，而代码里又显式写了这个文件 —— 同一行写了两遍。

**修法**
识别出这个叠加关系。统计调用次数时必须把它算进去：
改动前看到的 1406 条 `setSleepDisabled`，实际是 **703 次调用**，
而 703 恰好对应「35 分钟 ÷ 3 秒」的对账周期 —— 这个巧合才对上账。

**教训**
- 看到「重复」先怀疑输出管道，再怀疑业务逻辑。
- **日志行数不是调用次数。** 用日志量推导行为时，先确认一行的语义。

## 3. GitHub 的 `/releases/latest` 不返回预发布版本

**现象**
自动更新实测报 `HTTP 404`，据此得出「仓库还没有 Release」的结论 ——
但仓库里明明有一个。

**根因**
`/releases/latest` **只返回正式版**。本仓库的发布习惯是标 Pre-release，
于是接口返回 404：不是「资源不存在」，而是「没有符合条件的资源」。

**修法**
改成拉 `releases?per_page=30`，丢掉 draft、**保留 prerelease**，
再用版本号比较自己挑最高的一条。

**教训**
- **404 不等于「不存在」。** 接口的筛选语义（只要正式版）和使用场景
  （自己的仓库全是预发布）不匹配时，同样会 404。
- 排查时不要用「它报了 A，所以结论是 B」的跳跃；先把 A 的确切含义搞清楚。
- 出这个结论时用户说「仓库已有一个 Release，不可能没有」——
  **用户对自己系统的了解通常比一次探测的结论更可靠**，值得回头复核。

## 4. 更新器脚本的回滚分支会删掉用户的应用

**现象**
代码审查/编写时，更新器脚本的失败分支写的是「先 `rm -rf` 清干净，再放新版本」。
这个写法看起来比「先挪走」更稳妥 —— 实际上它是最危险的。

**根因**
如果「挪走旧版本」那一步失败（磁盘满、权限不足、文件被占用），
那么：

1. `rm -rf "$TARGET"` 会把**用户的应用直接删掉**
2. 回滚 `mv "$OLD" "$TARGET"` 因为备份**根本不存在**而同样失败
3. 结果：应用彻底没了

**修法**
改成两层嵌套判断，**并且回滚分支里绝不删目标路径**：

```sh
if mv "$TARGET" "$OLD"; then          # 旧的挪走了，才有备份可言
    if mv "$SOURCE" "$TARGET"; then   # 新的放进去了
        清理、重开
    else
        mv "$OLD" "$TARGET"; 重开     # 放不进去就把旧的放回原位
    fi
else
    重开                              # 旧的压根没动，原状未被破坏
fi
```

验证方式：造两个假 `.app`，一个当旧版本、一个当新版本，
跑真实生成的脚本 —— 正常替换、替换失败回滚、目标不存在三种场景。

**教训**
- **「先清理再写入」在覆盖场景里是陷阱。** 它把「能否恢复」的前提
  （备份存在）建立在自己刚删掉的东西上。
- 这个 bug 是被 `--update-script`（打印脚本但不执行）**在开发期暴露出来的**。
  危险动作的 dry-run 出口不是装饰，要留着。
- 涉及「替换正在运行的东西」的逻辑，验证必须覆盖**失败路径**，
  而不仅仅是顺利路径。

## 5. 跨进程释放断言会被内核拒绝

**现象**
曾以为别的程序可以取消 Deep Sleep 持有的断言，因此设计了一套「重申请」机制。

**实测结论**
断言归创建它的进程所有。跨进程释放返回 `kIOReturnNotPermitted`。
系统把断言的贡献者明确列为创建者：
`sleep 1 (sleep prevented by UURemote, powerd, Deep Sleep)`。

**唯一的失效途径是创建它的进程死亡** —— 而这正是对账要覆盖的场景
（助手被重启后，旧断言随旧进程消失，新进程什么都不持有）。

**教训**
- 不要基于猜测设计防御。先做一次最小实验（`scripts/try-release-assertion.swift`
  就是为这个问题留下的）。
- 验证过的结论要写下来，否则下一个人会重新怀疑一遍。

## 6. 无法确定「是哪个进程改了 pmset 设置」

**现象**
需要一个「谁改了我的设置」的答案。

**实测结论**
macOS **没有公开 API** 提供这个信息。
`pmset -g log` 只有睡眠/唤醒事件，**不含设置变更记录**，对这个需求没有帮助。

**处理方式**
不猜进程名。「外部活动」页只给能确定的事实：
改了什么、从什么变成什么、什么时候、**以及是不是 Deep Sleep 自己改的**
（我们跟踪自己的写入，所以能明确排除自己）。
另外单独列出「具备改电源设置能力的运行中程序」作为线索，
但明确标注这是**能力**而非**归因**。

**教训**
- 归因诚实是硬要求。给一个猜的进程名，比不给更糟 ——
  它会让人往错误方向排查，还会损害所有其他结论的可信度。
- 「列出可疑对象」和「指出凶手」要说成两件事。
  代码里的措辞是「程序里包含相关代码，可能自行修改」而不是「它改了」。

## 7. 关于「谁改了 disablesleep」，一个被实测推翻的推断

**现象**
`SleepDisabled` 的值被观察到从 1 变成 0。

**曾经的推断（错的）**
「它存在 `/Library/Preferences/com.apple.PowerManagement.plist` 里，
被某个外部程序改写了。」

**推翻它的实测**
用「20 分钟每 10 秒采样」的观察脚本抓到变化时刻：

```
[20:00:36] SleepDisabled -> 1
[20:06:09] SleepDisabled -> 0     ← 此刻那个 plist 的 mtime 仍是 20:00:13
```

mtime 没动 → **这个键根本不在那个 plist 里** → 推断错误。

**真正的线索**
- 助手日志显示那一刻**只有心跳查询**，历史上 `enabled: 0` 出现 **0 次**
  → 不是 Deep Sleep 改的
- 系统日志：`2026-09-27 20:06:07 powerd: Energy Saver Prefs have changed`
- 同期 `AlDente[1834]` 每 2 秒连一次 `com.apple.iokit.powerdxpc`
- AlDente 的二进制里直接含 `completelyDisableSleep` / `isSleepDisabled` /
  `Failed to execute pmset command:`，并调用 `pmset`

**结论**
- 「日志每 3 秒报一次被改回」是**自身 bug**（见第 1 条，TAB 解析）
- 「系统值确实被改过」是**外部干预**（AlDente 自带「完全禁用睡眠」）

两者是**两个独立的问题**，一开始被混成了一个。

**教训**
- **两个现象同时存在，不等于它们是同一个原因导致的。** 先分开验证。
- 推断要能被实验否定。设计验证时优先找「能一次判定真伪」的观测
  （这里是 plist 的 mtime），而不是能支持自己推断的旁证。
- 文件时间戳是很好的判据：内容变了但 mtime 没变，说明改的不是这个文件。

## 8. 菜单栏不能用 SwiftUI 的 `MenuBarExtra`

**原因**
`MenuBarExtra` 的点击一律弹出它自己的面板，**无法区分左右键**，
做不到「左键打开主界面、右键弹快速设置」。

**做法**
用 AppKit 的 `NSStatusItem` 手动搭建。菜单每次弹出都重新构建，
所以勾选状态永远是当下的真实状态，不需要订阅同步。

需要 root 的那一项在没启用完全控制时标注「需先启用完全控制」，
而不是点了没反应。

**教训**
系统集成类的需求，SwiftUI 的封装经常不够用。
遇到「做不到某件具体的事」时，及时退到 AppKit，不要硬凑。

## 9. Dock 图标必须动态切换，且最小化窗口也算「有窗口」

**原因**
关掉所有窗口后应用应该继续在菜单栏后台运行，所以切成 `.accessory` 让 Dock 图标消失。

**坑**
**最小化的窗口仍然算「有窗口」** —— 否则 Dock 图标一消失，
用户就再也找不回那个最小化的窗口了。

另外关掉窗口后从访达或聚焦再次打开，走的是 `applicationShouldHandleReopen`，
需要把界面叫回来。

**教训**
「隐藏入口」这类优化必须同时保证**还有别的路能回来**。否则就是让用户丢失东西。

## 10. CLI 输出多行时必须逐行加前缀

**现象**
`--update-script` 打印更新器脚本全文时，解析方拿到的内容切不干净 ——
日志噪音和脚本正文混在一起。

**根因**
`emit()` 原本只在**整段文本**前面加一次 `deepsleep: ` 前缀，
多行输出的后续行没有前缀，解析方只能靠猜来切分。

**修法**
`emit()` 改为按行拆分，**每一行**都加前缀。

**教训**
设计机器可解析的输出时，「只有第一行有标记」是个常见的疏漏。
要么每行都有标记，要么用明确的起止标记包起来。

## 11. `pgrep` 助手进程名是点号分隔

**现象**
查助手进程时搜 `deepsleep-helper`，没找到，一度误判成「助手进程已退出」。

**真相**
助手的**进程名**是 `com.skyc8266.deepsleep.helper`（点号），
`deepsleep-helper` 是 bundle 内的**文件名**形式。两个不一样。

```sh
pgrep -fl "com.skyc8266.deepsleep.helper"     # 对
```

**教训**
「查不到」在得出结论之前，先确认**查询条件本身**是对的。
这和项目里的另一条经验一致：写错的搜索模式会制造假的阴性结果。

## 12. 用人工维护的构建号判断助手是否需要更新（已废弃）

**背景**
最初的设计是：应用侧维护一个整数 `helperBuild`，
「改 `DeepSleepHelper/` 下的代码就 +1」，靠它判断已装的助手是否落后。

**为什么废弃**
1. **依赖人记得改。** 忘改 = 「明明修好了却不更新」；
   改错（跳号后又引用旧值）= 「每次启动都更新一遍」。
   任何需要人手动维护的判据都有这个毛病。
2. **不精确。** 只改了应用代码、没动助手时，版本号判据会认为助手要更新 ——
   白下载一次、白重启一次进程，什么都没变。

**现在的做法**
比对**两份二进制的内容摘要**（应用包内那份 vs 系统里装着那份）。
不需要维护任何数字，而且「助手代码有没有变」正是真正要问的问题。
它同时天然收敛 —— 替换成功后两边摘要必然一致，下一次不会再触发。

**教训**
判据优先选**能自动推导**的。这条原则在这个项目里出现了三次：

| 场景 | 人工维护的判据（弃） | 自动推导的判据（用） |
| --- | --- | --- |
| 助手是否需要更新 | 构建号 | 二进制内容摘要 |
| 应用是否有新版本 | 额外的发布序号 | 版本号（本来每次发布就会改） |
| 文档是否过期 | 「记得更新」 | `scripts/check-docs.py` 比对代码 |

## 13. `IOPMCopyAssertionsByProcess` 的调用方式

**坑**
它的签名是 **out 参数 + 返回 `IOReturn`**，不是返回字典：

```swift
// 错：以为它返回字典
let dict = IOPMCopyAssertionsByProcess()

// 对：
var raw: Unmanaged<CFDictionary>?
let result = IOPMCopyAssertionsByProcess(&raw)
guard result == kIOReturnSuccess, let dict = raw?.takeRetainedValue() else { ... }
```

**教训**
IOKit 大量使用 Core Foundation 风格的 out 参数 + 保留计数返回。
照着 Swift 的习惯猜签名会浪费很多时间，先查头文件。

## 14. 必须用 `open` 启动应用才能得到真实的启动行为

**现象**
直接执行 `"Deep Sleep.app/Contents/MacOS/Deep Sleep" --window-self-test`
时窗口不会创建。

**根因**
那条路径没有经过 LaunchServices，应用的激活策略与窗口行为跟真实启动不同。

**做法**
验证一律用：

```sh
open -a "…/Deep Sleep.app" --stdout /tmp/out.log --stderr /tmp/err.log --args <参数>
```

`--stdout` / `--stderr` 让输出可收集，`--args` 传参。

**教训**
自动化验证要尽量走**和用户一样的路径**。绕过系统的捷径会让验证结果失去意义。

## 15. 文档过期比没有文档更糟

**现象**
一个「维护文档」写好之后，代码继续改，文档没人动。
半年后新来的人照着文档操作，得到的是错误的结论 —— 而且他不会怀疑文档。

**处理方式**
不靠「记得更新」，靠两条机制（详见 [README.md](README.md)）：

1. **机器能查的交给机器**：`scripts/check-docs.py` 比对
   文档里的 CLI 参数表、协议命令表、版本号与代码是否一致
2. **机器查不了的定好触发条件**：改什么就同步哪份文档，列成表格

**另外一条原则**：文档里**少写会变的数字**。
不写行号（天天变），需要引用时写符号名（`HelperConstants.socketPath`）
而不是它的值。

**教训**
任何依赖人记性的东西都会失效。这条在文档、版本号、构建号上完全一样 ——
**能自动校验的，就不要靠自觉**。

## 16. 两个实例同时跑，助手侧断言会被来回抢

开发期最容易撞上的一条：机器上装着 `/Applications/Deep Sleep.app`（旧版），
你又从 `build/Build/Products/Debug/` 跑一份新的 —— 两个进程 bundle id 相同，
macOS 允许它们并存，而助手侧的断言是**按类型单槽存储**的（`identifiers[kind]`）。

于是两边的 3 秒对账各自认为「助手持有的和我的期望对不上」：一边申请、另一边释放，
助手日志里就会出现每 3 秒一次的 `acquireAssertion` / `releaseAssertion` 来回抖动，
看起来像助手坏了。

**排除法**：杀掉构建产物那份实例，抖动立刻停止 —— 说明是两边打架，不是对账逻辑坏了。
**做法**：测新版之前先退出已安装的那份
（`osascript -e 'tell application "Deep Sleep" to quit'`）。

顺带解释另一件容易误判的事：新版应用启动时会按内容摘要把助手**自我更新**成自己包内那份，
而旧版应用启动时又会把它推回旧摘要 —— 两边同时跑，助手会被反复替换重启。
一次只跑一份就没有这个问题（发布后用户机器上只会出现一种组合）。

## 17. 造测试用的进程探针：`cp /bin/sleep` 与 shell 脚本都不行

快速退出需要「一个能被杀、又带子进程」的探针应用。三种写法只有一种可用：

| 写法 | 结果 |
| --- | --- |
| `cp /bin/sleep` 到 `Xxx.app/Contents/MacOS/Probe` | 复制出来的二进制签名与路径不匹配：`open` 报 `RBSRequestErrorDomain Code=5 … Launchd job spawn failed`，直接跑会被内核 `SIGKILL` |
| 可执行文件写 shell 脚本 | 能跑，但进程名（`p_comm`）是 `bash`，测不出任何「按进程名」的规则 |
| 现场 `clang` 编一个小 sleeper | ✅ 带 ad-hoc 签名能跑，且 `p_comm` 就是文件名 |

```c
#include <unistd.h>
int main(void) { for (;;) { pause(); } return 0; }
```

要看树形结构就让 sleeper 自己 fork/exec 几个子进程。
「进程名到底是什么」只能靠 `ps -o pid,comm,args` 确认，不要推断。

**另一条**：伪装用的探针要么用无关的 bundle id，要么指向**当前没有在运行**的系统组件 ——
否则名单判定一旦出错，被杀的会是真正的系统进程。

## 18. App Shortcuts 的两条编译期硬规则（以及 macOS 上不存在的 API）

1. 每条短语**必须**包含 `\(.applicationName)`，否则编译期报错 —— 系统靠它做语音消歧。
2. 短语是**编译期常量**，不能用运行时字符串拼出来。

于是短语不可避免地要写两遍：给编译器的类型化短语、和给人看的纯文本
（界面区块、`--automation` 输出、文档都读后者）。两份由 `check-docs.py` 逐条比对。

迁移时踩到的编译错误：

- `cannot find 'ShortcutsLink' in scope` —— `ShortcutsLink` 只存在于 iOS。
  macOS 上跳到「快捷指令」App 用 `Link(destination: URL(string: "shortcuts://")!)`。
- `type 'ShortcutTileColor' has no member 'indigo'` —— 合法值是
  `red/orange/tangerine/yellow/lime/teal/lightBlue/blue/navy/grape/purple/pink/grayBlue/grayGreen/grayBrown`。

还有一条**不是错误但会让人误会**的日志：从 `build/` 里直接跑的应用会打印
`Unable to re-register with Process Instance Registry … com.apple.linkd.autoShortcut`。
那是 Spotlight / 快捷指令的索引服务不认这个位置的应用，属正常现象；
把应用放到 `/Applications` 之后就没有了。

## 19. 普通权限读不到 root 的进程 —— 「读不到」不等于「不存在」

`proc_listpids` 能列出所有 pid，但 `proc_pidinfo` 对**别的用户（尤其 root）拥有的进程会失败**，
于是快照里根本没有它们。实测：非 root 跑一遍，351 个进程里 uid=0 的有 **0** 个。

这个事实直接引出两个坑：

1. 应用侧算出的计划天然覆盖不到 root 进程 ——
   所以「结束由 root 拥有的进程」这件事**必须**走助手。
2. 更隐蔽的一个：最初把「快照里找不到这个 pid」当成「进程已经退出，忽略」，
   于是用户按下快捷键后看到的是「什么都没发生，也没有原因」。
   现在这种情况会记为一条**拒绝记录**，理由写明「无法读取该进程
   （可能刚刚退出，或由其他用户运行而需要完全控制）」。

**教训**：在权限受限的查询里，「查不到」是一个需要上报的结果，不是「不存在」。
这与项目里「归因要诚实」是同一条原则。

## 20. 全局快捷键用 Carbon `RegisterEventHotKey`，别用 NSEvent 监听

`NSEvent.addGlobalMonitorForEvents` 需要「输入监控」权限 —— 一个睡眠管理工具不该为了
一个快捷键去要这种权限，而且用户拒绝授权后功能会**静默失效**。

Carbon 的 `RegisterEventHotKey` **不需要任何权限**，实测注册成功。
代价是写法老派（`EventHotKeyID` + `InstallEventHandler`），换来的是「装完就能用」。

另外：注册失败（组合被别的程序占了）**必须把原因告诉用户** ——
`--hotkey-status` 与界面上的状态标签就是为此存在的。
「按了没反应」不解释，用户只会认为功能坏了。

## 21. 用户可见文案里不要出现 `\\(` —— 它会原样显示

Swift 的插值是 `\(...)`。一旦写成 `\\(...)`（多一个反斜杠），编译器**不会报错**：
它把 `\\` 当作转义后的反斜杠，于是界面/日志里原样显示 `\(engine.targets.count)`。

发布前被用户当场看到过一次（「名单数量那里一直写的是 `\(engine.`」）。

**防呆**：`scripts/check-docs.py` 会扫全部 Swift 源码里的 `\\(`，命中即失败。
这属于「机器能查的别靠人记」—— 肉眼审 UI 文案很容易漏掉一个反斜杠。

## 附：排查问题的通用姿势

从这个项目的经历里提炼出来的：

1. **先分开再合。** 两个同时存在的现象不一定是同一个原因（第 7 条）。
2. **要能被否定的证据。** 找那种「如果是这样，那一定不会那样」的观测，
   而不是支持自己推断的旁证。
3. **系统说的才算。** 应用自己的日志是自述。
   `pmset -g`、`launchctl print`、`ioclass` 这些才是事实。
4. **查不到先怀疑查询条件**（第 11 条）。
5. **失败路径必须验证**（第 4 条）。顺利路径跑通不代表逻辑正确。
6. **别人的口头结论也可能是错的**，包括用户和 AI 的。
   但用户对自己系统的了解通常比一次探测更可靠（第 3 条）。
7. **被推翻的推断也值得记下来**（第 7 条）——
   否则下一个人会沿着同一条错路再走一遍。
